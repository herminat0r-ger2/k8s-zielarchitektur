KRITIS Zielarchitektur — Proxmox + Kubernetes

2 Standorte · 4 Kubernetes-Cluster · Legacy-Metro + Ceph in den Standorten · Werkzeuge & Erläuterungen getrennt darunter

DR-Modus:
Aktiv / Passiv: Standort A trägt die Produktion, Standort B ist DR-Standby. Einfach und split-brain-sicher — aber die Hardware in Standort B bleibt ungenutzt, bis ein Failover sie braucht.
Aktiv / Aktiv: Beide Standorte produktiv — Stateless-Services beidseitig, Datenbank-Primary in A mit Read-Replicas in B. Hardware wird in beiden Datacentern genutzt; Split-Brain bleibt dank Single-Primary-Writes aus.

Hardware

  • • Enterprise-Server (z.B. HPE Gen10) → Proxmox VE
  • • 2 Ressourcen-Pools (Datacenter A, Datacenter B)
  • • Multi-100-Gb/s Metro-Link
  • • Cisco ACI als L3-Transport
  • • Lokal: NVMe (Betriebssystem + etcd), NVMe/SSD als OSD

Kubernetes

  • • 4 Cluster: Prod-1 (aktiv), Prod-2 (DR), Test, Quality
  • • Nodes = VMs im Proxmox-Pool (Talos Linux oder RKE2)
  • • Cilium CNI + NetworkPolicies, Hubble Observability
  • • ClusterMesh für standortunabhängige Services
  • • Tenants = Namespaces + RBAC

Storage & DR

  • • 2× Ceph (je Datacenter) + async Replikation (Patroni/RBD-Mirror)
  • • Metro-VMs als eigenes Cluster über beide Datacenter
  • • Velero + Proxmox Backup Server + MinIO
  • • etcd lokal auf NVMe (nie Ceph)
  • • Veeam wird durch Proxmox Backup Server + Velero ersetzt
